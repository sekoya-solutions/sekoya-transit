# Agent Instructions — transport-tycoon-2

Standing rules for **every** AI agent/model/chat working on this project. At the start of every session, read this file, [docs/roadmap.md](docs/roadmap.md), and the **current ISO-week** chat-history file under [docs/chat-history/](docs/chat-history/README.md) when it exists locally. Do not load the full chat archive by default.

## 1. Project context

- Transport Tycoon-style game. Inspirations: Transport Tycoon Deluxe (TTD) and Rise of Industry (the first one).
- Engine: **Unity 6.3 LTS** (latest 6000.3.x patch; never 6000.5.x; evaluate 6.7 LTS later, ADR 0015), 2D Universal Render Pipeline (URP), UI Toolkit, pure C# deterministic simulation with commands (see [docs/adr/](docs/adr/README.md); ADRs are the source of truth for technical decisions, read them before coding). Other stack details are decided via ADR with owner approval.
- Product discovery decisions are documented in [docs/specs/product-vision.md](docs/specs/product-vision.md), the scope reference (V1/V2/V3+); detailed rules are in [docs/specs/gameplay-systems.md](docs/specs/gameplay-systems.md). Check both before proposing features. Product documents may remain marked Draft pending owner review. All balance values must be data-driven.
- Hard architectural constraints: simulation separated from presentation and deterministic, player actions as commands (future AI opponents in V2, multiplayer in V3+); maps up to 512x512 (sizes S/M/L = 128/256/512); internationalization (i18n) compatible code (English only in V1); robust automated regression tests and continuous integration.
- Owner availability: 20-40 h/week; end of 2026 is an aspiration, not a deadline. Unity version and render pipeline are chosen by the assistant (propose via ADR for approval).
- Targets: Windows PC and WebGL demo.
- Vibe-coded in the sense that the owner steers via chat and AI writes code, but this is a personal project assisted by AI, not a quick delivery.
- Primary purpose: **portfolio** showcasing the owner's skills. Commercial success is secondary.
- Owner: Tech Lead, 15+ years of experience. Very rigorous. Reviews every technical choice and most of the code.
- **Early-collaboration pace (until the owner relaxes it):** for the first issues with a new agent/tooling setup, go slowly and keep autonomy low. Prefer asking before acting when unsure about sequence, decision ownership, or tool use—e.g. whether to do A before B, whether to decide X yourself or ask the owner, and whether a given tool/program/API/action is OK. Optimize for workflow validation and trust calibration over speed.
- **Design decisions for the owner:** when asking the owner to choose between options (gameplay, UX, architecture, scope), do not assume game-dev jargon is clear. For each choice: explain what it means in plain language (what the player sees/does, or what changes in the code/product); give pros and cons when there are alternatives; and state a recommended default for this portfolio prototype when one option is clearly better. Keep the recommendation brief and say why.
- **No software installs without approval:** never install, upgrade, or uninstall software on the owner's machine (winget, MSI, setup.exe, global npm/pip, Docker images pulled solely to get a tool, etc.) unless the owner explicitly approves that specific install in the current turn. Prefer repo-local / portable / already-present tools. If a required tool is missing, ask first.
- **Standalone documentation changes:** when `AGENTS.md` or other tracked documentation is changed outside an in-progress issue, commit the changes on a focused branch and open a pull request. Issue wrap-up is the exception: put its roadmap update in the issue branch's final pre-merge commit; do not open a separate wrap-up pull request. Chat-history log files are local-only and must never be committed (see section 3).
- **Issue PR wrap-up timing:** when the owner authorizes merging an implementation PR, first make one final commit on that same issue branch updating `docs/roadmap.md` to point to the next issue (also include `AGENTS.md` if a standing rule changed). Push the commit, wait for CI to pass, then squash-merge the implementation PR. Never create a separate post-merge wrap-up commit or PR. Do not add a closing keyword or otherwise link a docs-only PR to the implementation issue; the implementation PR is the one that closes the issue.
- **Feature branches:** when starting work on a GitHub issue, create the conventional feature branch from up-to-date `main` without asking (e.g. `feat/<n>-short-slug`). Still ask before merging, force-pushing, or other irreversible git actions.
- **No direct commits to `main`:** always land changes via a feature branch and pull request. Do not commit or push straight to `main` unless the owner explicitly authorizes a one-off exception in that turn.
- **Squash-merge into `main`:** always merge authorized pull requests with `gh pr merge --squash` ([ADR 0005](docs/adr/0005-repository-layout-and-git-workflow.md)). Never use classic merge (`gh pr merge` / `--merge`) or rebase-merge (`--rebase`) unless the owner explicitly authorizes a one-off exception in that turn. Omitting `--squash` is wrong for this repo—it creates a merge commit and noisy history.
- **Unity Hub/Editor:** the agent may launch and drive the pinned Unity Editor as needed to generate `.meta` files, scenes, imports, and to run EditMode tests or builds. Prefer doing this in-agent so the owner does not have to open Unity for routine work.
- **Visual WebGL preview (when the owner asks):** build a real Unity WebGL player for the relevant `_Project` scene (batchmode `-buildTarget WebGL` + scene-specific `-executeMethod`; no HTML mocks). Use a **Development** build (`BuildOptions.Development`) with WebGL code optimization set to shorter build times (`BuildTimes`), not a release/LTO player—local previews optimize for build speed. Use a **stable, issue-agnostic** output path under ignored `Builds/` (e.g. `Builds/MapPlayWebGL`)—do not embed GitHub issue numbers in preview build paths or serve scripts. Serve on `http://127.0.0.1:8765/` (PowerShell `HttpListener`, loopback-only; no new installs). **Serve correctly the first time:** do **not** use `Start-Job` / agent-shell-tied background jobs for the static server—they die or race and the in-app browser then hits a connection error. Write a small serve script under ignored `Builds/` (e.g. `Builds/serve-mapplay-8765.ps1`), start it with **`Start-Process powershell.exe -WindowStyle Hidden -PassThru`** (detached), record the PID in `Builds/MapPlayWebGL-serve.jobid.txt`, **probe `Invoke-WebRequest http://127.0.0.1:8765/` for HTTP 200**, then open that URL in the agent tool's in-app browser pane beside the chat (Cursor browser, or the Claude Code desktop built-in browser). **When the owner confirms the preview is validated (or is done), always stop the :8765 server (kill the recorded PID) and close the in-app browser tab in the same turn**—do not leave either running. Keep preview URLs excluded in `.lychee.toml` (`localhost` and `127.0.0.1` on port 8765).

## 2. Quality and working rules

- Apply state-of-the-art coding practices; no quick hacks.
- Documentation must be perfectly ordered, accurate, and kept in sync with the code.
- Justify every significant technical choice (trade-offs, alternatives considered) and get the owner's approval before adopting it. Record accepted decisions in the docs.
- Keep changes reviewable: small, focused, well-explained.
- **Cost-efficient execution without quality trade-offs:** avoid unnecessary model and tool usage, such as repeated CI polling, redundant repository reads, or rerunning checks that a change does not affect. Batch independent reads and related operations, and use completion notifications or a single CI status check when results are needed rather than polling repeatedly. Use economical model settings for routine work and reserve higher-cost models for tasks that benefit from their additional capability. Never reduce code quality, test coverage, security, documentation accuracy, reviewability, or required verification to save cost; optimize redundant overhead only.
- **Delegate to economical subagents when quality holds (owner-authorized standing rule):** when the tooling supports it (e.g. Claude Code's Agent tool with a `model` override), give self-contained, mostly mechanical or read-heavy subtasks to a subagent on an economical model (Sonnet or Haiku) instead of the main model. Examples: wide code or documentation searches, finding every usage of an API, inventorying files, summarizing long logs or test output. Keep on the main model: design decisions, acceptance-criteria drafting, ADRs, Core determinism and save-format code, hard debugging, final review, and anything that depends on the current conversation's context. Skip delegation when the job is only a few tool calls, since a subagent starts cold and re-reads context. Treat a subagent's report as input, not proof: verify the parts you act on. Whenever you delegate, state in your message which model the subagent runs on and what it is doing (e.g. "Handing the usage search to a Haiku subagent").
- **Unity validation and Actions budget:** run hosted Unity EditMode automatically only on pushes to `main` that change `TransportTycoon2/` or the Unity workflow (ADR 0021)—not on pull requests. Keep hosted Windows and WebGL platform builds on-demand only (never automatic on PR or `main`). Before opening a PR that changes `TransportTycoon2/`, run local EditMode on that head (ADR 0030); re-run before merge if the head moved without a new local pass. When the owner authorizes merge, proceed immediately with the wrap-up commit and squash-merge—do **not** ask about (or delay for) a local WebGL player/preview at that point, even if Presentation or other ADR 0030 WebGL-risk surfaces changed and WebGL was not run. Offer or run WebGL only when the owner asks in that turn (or earlier, before merge authorization). Never auto-start WebGL or a served preview. Do not require a local Windows player build by default. Do not run local player builds before creating the PR unless the owner asks for an early preview. Skip local Unity player builds for documentation- or workflow-only changes; the independent .NET and Markdown CI checks still run as configured.
- **Proportionate scope:** Before discretionary cleanup or tooling work, weigh measurable expected benefits (performance, shipped size, reliability, maintainability, or security) against implementation/validation time and regression risk. Keep work focused on the requested outcome; do not expand into low-impact cleanup solely for tidiness. Defer or ask before optional work when its benefit is unclear, without skipping required verification.
- **AI art iteration:** If a generated image misses the asset's required composition or shape, revise the prompt and regenerate instead of repeatedly cropping or heavily modifying a poor fit. Use post-processing only for limited, purposeful curation of a suitable result. If curation or import loses clarity, fix that processing step before regenerating. Issue #16 validates ComfyUI feasibility only; do not present its pilot outputs or workflow as production-ready. Workflow quality and in-game art placement remain future work.
- **Unity visual review:** When asked to review Unity scenes or game visuals in a browser, use an actual Unity WebGL build/render where feasible; do not substitute a hand-authored HTML mockup unless the owner explicitly requests one.
- C# language level is **C# 9** (what Unity 6.3 compiles): no file-scoped namespaces, no `init`/records without polyfill, no C# 10+ features in Core. `#nullable enable` at the top of every Core file. Test method names use `Method_Scenario` style.
- Run `dotnet test dotnet/TransportTycoon.Core.Tests` and `dotnet format dotnet/TransportTycoon.Core.Tests --verify-no-changes` before every commit touching C#. Files must use LF line endings (run `dotnet format whitespace` if an editor wrote CRLF).
- Git: trunk-based, feature branches and pull requests, squash-merge into `main` via `gh pr merge --squash`, Conventional Commits (feat:, fix:, docs:, refactor:, test:, chore:, ci:). Unity project lives in `TransportTycoon2/` (ADR 0005, 0016). Standards are in ADR 0006; a feature is not done without tests (ADR 0007); CI per ADR 0008. AI tool attribution stays as the tool emits it (e.g. Claude Code's `Co-Authored-By` commit trailer and "Generated with Claude Code" PR footer); do not strip it.
- Always spell out an acronym the first time it is used in a document or reply (e.g. "Architecture Decision Record (ADR)").

## 2b. Documentation and project management

- **Docs-as-code:** all documentation is Markdown in this repository, which is the single source of truth. Notion is not used (unreliable agent integration).
- Docs layout (create as needed): `docs/specs/` (feature/system specs), `docs/adr/` (Architecture Decision Records, one per significant technical choice), `docs/roadmap.md` (high-level milestones and current next work), `docs/chat-history/` (local-only append-only weekly conversation logs, gitignored except the README; see that folder’s README).
- Use GitHub tooling for management: Issues for tasks/bugs, milestones and a GitHub Project board for the roadmap/dashboard, pull requests for changes. Use the `gh` CLI or GitHub MCP, and check for existing issues before creating new ones (avoid duplicates).
- **Epic status:** when starting work on a child issue, set both the child issue and its parent epic to In Progress on the Project board; verify both statuses.
- **Issue delivery:** finish every required delivery step for the issue before stopping—implementation, docs/ADR updates, local verification (`dotnet test` / format when C# changes; local Unity EditMode when `TransportTycoon2/` changes per ADR 0030; Unity `.meta` / scene wiring when needed), then always commit, push the feature branch, and create a pull request for owner review. Do not ask whether to open the PR, and do not pause mid-issue waiting for permission to complete those steps. The only optional step that needs explicit owner permission is a local WebGL player/preview build (see Unity validation rules). Leave the pull request open and wait for owner feedback (changes requested, or explicit go-ahead to merge). Do not merge unless explicitly authorized.
- **Issue closure gate:** never close a GitHub issue or mark its Project item Done while its implementation pull request is still open. Close it only after the PR is merged and the acceptance criteria are verified against the merged result. Prefer the PR's closing keyword to close the issue on merge; keep the board status synchronized. If an issue is closed prematurely, reopen it and restore an active board status immediately.
- **Acceptance checklist:** tick each acceptance-criteria checkbox in the issue body as soon as it is verified (against the merged result), before or when closing the issue. Never close an issue with verified criteria unticked; leave a criterion unticked and say why if it is not yet verified.
- **PR Test plan checklist:** tick each Test plan checkbox in the pull request body as soon as that item is verified (local tests, each green CI check, owner-validated preview, etc.). Do this before asking to merge when possible; if merge already happened with boxes still open, update the merged PR body in the same turn. Never leave verified Test plan items unticked.
- **PR checklist completion:** before completing or merging a PR, resolve every checklist item: check it when verified, or check it with a clear not-applicable explanation when it does not apply. Never leave unchecked items on a completed or merged PR; update the saved body of a merged PR in the same turn if needed. Do not imply that inapplicable work (such as feature tests for a documentation-only change) was performed.
- **PR-issue linkage:** every pull request must be created from `.github/pull_request_template.md` and its body must contain a closing keyword for its issue (`Closes #N`) so GitHub links them. Before marking a PR ready or merging, verify `closingIssuesReferences` (e.g. `gh pr view N --json closingIssuesReferences`) lists the issue; fix the body if empty.
- **ADR index integrity:** keep exactly one index row per ADR number, and ensure its title, link, and status match the ADR file. Before finishing an ADR change, search the index for that number and verify it occurs exactly once.
- Docs must stay portable (validated by the owner): standard Markdown only (relative links, no Obsidian wikilinks or plugin-only syntax), so they render on GitHub and in Obsidian. Diagrams use Mermaid code blocks.
- **Markdown verification:** after modifying any Markdown content—including GitHub issue or pull request descriptions—inspect the resulting text to confirm paragraphs, headings, lists, and checkboxes retain their intended structure. Before **every commit** that touches tracked `.md` / `.markdown` files, run `powershell -NoProfile -File scripts/check-markdown.ps1` (or the same `markdownlint-cli2` + `lychee` commands it wraps, over `git ls-files -- '*.md' '*.markdown'`) and fix failures first. Do not skip the checks; if `lychee` or `markdownlint-cli2` is missing, ask the owner before installing (see no-software-installs rule). Preferred layout (gitignored): portable Node + `markdownlint-cli2` under `.tools/`, and portable `lychee` at `.tools/lychee/lychee.exe` (same major version as CI when practical)—not a system-wide winget install. Do not push Markdown that would fail the CI **Markdown lint and link check** job. For GitHub issue/PR bodies, retrieve the saved body and verify line breaks and checklist formatting rather than trusting the submitted text.
- **Safe GitHub issue/PR body edits:** a body edit once flattened issue #173 into one paragraph because the body was fetched as separate lines and glued back together. To prevent a repeat: (1) never round-trip a body through PowerShell string handling (`Set-Content`, `-replace`, `[IO.File]::WriteAllText` on a fetched body); fetch it with `gh ... --json body`, parse with `ConvertFrom-Json` so it stays one string (or edit via Bash with `sed`), and write it to a file without a byte-order mark (BOM, a hidden marker `Set-Content -Encoding utf8` adds) passed with `--body-file`; (2) after every edit, fetch the saved body again and check that the line count, heading count, and ticked and unticked checkbox counts match what you intended, and that the first line has no hidden character; (3) a checkbox count alone is not proof. Do this for every body edit, including ticking boxes after a merge.
- GitHub account/repo: `sekoya-solutions/transport-tycoon-2` (private for now). Labels (type/area/version) and milestones M0-M6 exist; use them on every issue. Use `gh` (`C:\Program Files\GitHub CLI\gh.exe` if PATH is stale). Branch protection is not available on private free repos: re-check when public or upgraded.
- Never hand-write Unity-generated files (ProjectSettings, Packages/manifest, .meta); let the Unity editor create them.
- Git on GitHub is the ONLY version control system. Never enable Unity Version Control (Plastic SCM) or any other VCS for the project.
- Obsidian may be used by the owner as a read-only-style viewer on `docs/`; it is not a dependency. `.obsidian/` must be git-ignored.

## 3. Mandatory: chat history logging (local only)

- Append every exchange (user prompt + assistant answer) to the **current ISO-week** file under [docs/chat-history/](docs/chat-history/README.md) **before ending the turn** (create the week file if it does not exist).
- Chat-history **log** files (week files and `archive/`) are **local-only** and **gitignored**. Never stage, commit, push, or include them in a pull request. Only [docs/chat-history/README.md](docs/chat-history/README.md) is tracked.
- Append only; never rewrite or delete past entries. Do not append to `archive/vscode-era.md` or to closed week files.
- Keep a single global entry counter across week files (continues after the archive).
- Entry format:

```text
## [N] YYYY-MM-DD HH:MM — <short title>
**User:** <verbatim or faithful prompt>
**Assistant:** <summary of answer + actions taken>
**Files changed:** <list or "none">
**Decisions / context for future agents:** <bullets>
```

## 4. Mandatory: maintaining this file

- Whenever the owner gives a general rule, preference, convention, or project-wide decision (anything that should outlive the current chat), add or update it in this file **in the same turn**, in the appropriate section. Do not leave it only in the local chat history.
- Keep this file concise, deduplicated, and organized. Edit existing rules rather than appending contradictions; if a new rule supersedes an old one, replace it.
- Note in the local chat-history entry when AGENTS.md was updated.
