# Agent Instructions — sekoya-transit

Standing rules for **every** AI agent/model/chat working on this project. The owner's general rules, valid in every project, are in `~/.claude/AGENTS.md`; this file adds the rules specific to this project and takes precedence where the two conflict. At the start of every session, read this file, [docs/roadmap.md](docs/roadmap.md), and the **current ISO-week** chat-history file under [docs/chat-history/](docs/chat-history/README.md) when it exists locally. Do not load the full chat archive by default.

## 1. Project context

- Sekoya Transit: a transport and logistics tycoon game (renamed from the working title "Transport Tycoon 2" in Issue #198 to avoid the trademark). Inspirations: Transport Tycoon Deluxe (TTD) and Rise of Industry (the first one).
- Engine: **Unity 6.3 LTS** (latest 6000.3.x patch; never 6000.5.x; evaluate 6.7 LTS later, ADR 0015), 2D Universal Render Pipeline (URP), UI Toolkit, pure C# deterministic simulation with commands (see [docs/adr/](docs/adr/README.md); ADRs are the source of truth for technical decisions, read them before coding). Other stack details are decided via ADR with owner approval.
- Product discovery decisions are documented in [docs/specs/product-vision.md](docs/specs/product-vision.md), the scope reference (V1/V2/V3+); detailed rules are in [docs/specs/gameplay-systems.md](docs/specs/gameplay-systems.md). Check both before proposing features. Product documents may remain marked Draft pending owner review. All balance values must be data-driven.
- Hard architectural constraints: simulation separated from presentation and deterministic, player actions as commands (future AI opponents in V2, multiplayer in V3+); maps up to 512x512 (sizes S/M/L = 128/256/512); internationalization (i18n) compatible code (English only in V1); robust automated regression tests and continuous integration.
- Owner availability: 20-40 h/week; end of 2026 is an aspiration, not a deadline. Unity version and render pipeline are chosen by the assistant (propose via ADR for approval).
- **V2 is incremental:** V1 is done (2026-10-29). V2 work is created as individual issues for fixes or evolutions, one at a time, with no full up-front backlog or new milestone plan unless the owner asks. Keep the product-vision scope table as the reference for what belongs in V2.
- **V2 issue workflow:** (1) turn the owner's prompt into a new GitHub issue (labels `version: V2` plus type/area, the milestone "V2 Incremental fixes and evolutions", added to the Project board); (2) ask the owner questions, with the plain-language option explanations required above, whenever the acceptance criteria cannot be written without them; (3) implement the issue through the usual feature branch, local verification and pull request; (4) when Presentation or gameplay changed, ask the owner whether to build and serve the local WebGL preview before asking for the merge go (this replaces "offer only on request" for such changes; still never start it before the owner says yes); (5) wait for the owner's go before merging, then follow the squash-merge rules. All other V1 rules still apply and need no restating in V2 prompts.
- Targets: Windows PC and WebGL demo.
- Vibe-coded in the sense that the owner steers via chat and AI writes code, but this is a personal project assisted by AI, not a quick delivery.
- Primary purpose: **portfolio** showcasing the owner's skills. Commercial success is secondary.
- **No folder links into shared folders (owner rule, 2026-11-18):** a clean-up removed an old worktree whose `.tools` was a Windows junction to the main folder's `.tools`, and the delete went through the link and wiped the main `.tools`. Never create junctions or symbolic links into shared folders: give a worktree its own tools or call the main folder's by absolute path. The general delete procedure for folder links applies.
- **Standalone documentation changes:** when `AGENTS.md` or other tracked documentation is changed outside an in-progress issue, commit the changes on a focused branch and open a pull request. Chat-history log files are local-only and must never be committed (see section 3).
- **Issue PR merge timing:** the roadmap is updated in the implementation PR's **first** commit (add the V2 issue to the delivered table in `docs/roadmap.md`), never in a final pre-merge commit, because V2 has no planned order and no "next issue" pointer to maintain. When the owner authorizes merging an implementation PR, make no extra commit: wait for CI to pass (include any `AGENTS.md` change in the issue branch earlier if a standing rule changed), then squash-merge the implementation PR. Never create a separate post-merge wrap-up commit or PR. Do not add a closing keyword or otherwise link a docs-only PR to the implementation issue; the implementation PR is the one that closes the issue.
- **Feature branches:** when starting work on a GitHub issue, create the conventional feature branch from up-to-date `main` without asking (e.g. `feat/<n>-short-slug`). Still ask before merging, force-pushing, or other irreversible git actions.
- **Unity Hub/Editor:** the agent may launch and drive the pinned Unity Editor as needed to generate `.meta` files, scenes, imports, and to run EditMode tests or builds. Prefer doing this in-agent so the owner does not have to open Unity for routine work.
- **Unity batchmode runs, never wait blindly (owner rule, Issue #316):** a run once stalled for 14 minutes: the shell's working directory had drifted into a subfolder, so the relative `-projectPath` was wrong and Unity quit at once ("Couldn't set project path"), while `Start-Process -Wait` kept waiting on the Unity licensing client that Unity had started and that outlives it. To prevent this: (1) pass absolute paths for `-projectPath`, `-logFile` and `-testResults` (never rely on the shell's current folder, which a previous `cd` can move); (2) never use `Start-Process -Wait`; start Unity with `Start-Process -PassThru` and wait on that process only (`$p.WaitForExit()`); (3) about 30 seconds after launch, check that the process runs or has exited and that the log exists, and read it for "Couldn't set project path" or other early errors; (4) if no completion arrives within the expected time (EditMode takes about 1 to 6 minutes; less when scripts are already compiled), read the log tail and the process state right away instead of waiting longer; (5) report the result from the log's "Test run completed" line and the results XML counts.
- **Visual WebGL preview (when the owner asks):** build a real Unity WebGL player for the relevant `_Project` scene (batchmode `-buildTarget WebGL` + scene-specific `-executeMethod`; no HTML mocks). Use a **Development** build (`BuildOptions.Development`) with WebGL code optimization set to shorter build times (`BuildTimes`), not a release/LTO player—local previews optimize for build speed. Use a **stable, issue-agnostic** output path under ignored `Builds/` (e.g. `Builds/MapPlayWebGL`)—do not embed GitHub issue numbers in preview build paths or serve scripts. Serve on `http://127.0.0.1:8765/` (PowerShell `HttpListener`, loopback-only; no new installs). **Serve correctly the first time:** do **not** use `Start-Job` / agent-shell-tied background jobs for the static server—they die or race and the in-app browser then hits a connection error. Write a small serve script under ignored `Builds/` (e.g. `Builds/serve-mapplay-8765.ps1`), start it with **`Start-Process powershell.exe -WindowStyle Hidden -PassThru`** (detached). Windows PowerShell here blocks `.ps1` files (execution policy) and the agent's auto-mode permission check denies `-ExecutionPolicy Bypass`, so do **not** run the `.ps1` with that flag: pass the same server code inline, Base64-encoded as UTF-16LE, with `-ArgumentList '-NoProfile','-EncodedCommand',$encoded` instead (inline commands are not subject to the policy; keep it loopback-only on :8765). A plain `-Command $code` breaks because `Start-Process` re-quotes the script's quotes and line breaks, so the server never starts. Record the PID in `Builds/MapPlayWebGL-serve.jobid.txt`, **probe `Invoke-WebRequest http://127.0.0.1:8765/` for HTTP 200**, then open that URL in the agent tool's in-app browser pane beside the chat (Cursor browser, or the Claude Code desktop built-in browser). **When the owner confirms the preview is validated (or is done), always stop the :8765 server (kill the recorded PID) and close the in-app browser tab in the same turn**—do not leave either running. Keep preview URLs excluded in `.lychee.toml` (`localhost` and `127.0.0.1` on port 8765).
- **Debugging a player's save file (owner rule, Issue #320):** when the owner gives a `.sav` file (from the in-game Debug button) with a bug, open it and find the cause before patching. (1) Data: copy it under ignored `Builds/` and run Unity batchmode with absolute paths (same rules as above) and `-executeMethod SekoyaTransit.Presentation.Editor.SaveFileReportCommand.RunFromBatch -saveFile <abs .sav> -reportDir <abs folder> [-advanceDays N]`; it loads the file through the game's migrations and restore, optionally runs N in-game days, and writes `report.md` (date, cash, routes, vehicles with stuck flags, contracts) plus `state-loaded.json` and `state-advanced.json` (the full state as plain JSON); exit code 1 and the reason in `report.md` when the file cannot be loaded. (2) Visuals, when the bug is on screen and the owner approves a WebGL preview: copy the file into `SekoyaTransit/Builds/MapPlayWebGL/` and open `http://127.0.0.1:8765/?save=<file name>`; Development builds load it at start (plain `.sav` file names from the page's folder only), release builds ignore the parameter.

## 2. Quality and working rules

- Apply state-of-the-art coding practices; no quick hacks.
- **Unhappy paths** cover every target: Windows and WebGL, slow machine or network.
- **Delegation:** besides the general list, keep acceptance-criteria drafting and Core determinism and save-format code on the main model.
- **Unity validation and Actions budget:** run hosted Unity EditMode automatically only on pushes to `main` that change `SekoyaTransit/` or the Unity workflow (ADR 0021)—not on pull requests. Keep hosted Windows and WebGL platform builds on-demand only (never automatic on PR or `main`), except the Deploy WebGL demo workflow, which builds and publishes to Pages automatically on `main` pushes that change `SekoyaTransit/` and publishes only if its build succeeds (ADR 0034). Before opening a PR that changes `SekoyaTransit/`, run local EditMode on that head (ADR 0030); re-run before merge if the head moved without a new local pass. When the owner authorizes merge, proceed immediately with the wrap-up commit and squash-merge—do **not** ask about (or delay for) a local WebGL player/preview at that point, even if Presentation or other ADR 0030 WebGL-risk surfaces changed and WebGL was not run. Offer or run WebGL only when the owner asks in that turn (or earlier, before merge authorization). Never auto-start WebGL or a served preview. Do not require a local Windows player build by default. Do not run local player builds before creating the PR unless the owner asks for an early preview. Skip local Unity player builds for workflow-only changes.
- **No simulation without a go (owner rule, Issue #307):** never run a balance simulation (`dotnet/SekoyaTransit.Balance`) unless the owner has given the go for that run; when a claim about the economy needs measuring, ask for the go first. Building the tool and running its tests are fine.
- **AI art iteration:** If a generated image misses the asset's required composition or shape, revise the prompt and regenerate instead of repeatedly cropping or heavily modifying a poor fit. Use post-processing only for limited, purposeful curation of a suitable result. If curation or import loses clarity, fix that processing step before regenerating. Issue #16 validates ComfyUI feasibility only; do not present its pilot outputs or workflow as production-ready. Workflow quality and in-game art placement remain future work.
- **Distance pay shape (owner rule, Issue #342):** every tile adds the same amount, with no bend; a longer delivery always pays more; and with the same cargo a vehicle on a longer route always earns more per year than on a shorter one. So `startPercent` must stay below `percentPerTile` × capacity × speed of every vehicle; a content test guards this.
- **Full-screen windows on top:** every full-screen shell window (Routes, Achievements, Vehicles unlock, and future ones) must draw above all other HUD elements (for example the active contracts box); in `MapPlayShell.uxml` declare such a window after every non-window element, the toast stack and side panels included, so UI Toolkit draws it last; only the modal panels (game over, new game, save / load, sound) may follow; `ShellDrawOrderTests` guards this (owner rule, Issue #286; Issue #354).
- **Upkeep shown per vehicle only:** never show the player an upkeep value per unit of cargo capacity, in any window, card or tooltip; show the upkeep of one vehicle, and for a train type the range from the locomotive with 1 wagon to the locomotive with its maximum wagons (owner rule, Issue #314). Per-unit rates stay internal to the data and the docs.
- **Same economy on every map size (owner rule, 2026-11-05, Issue #307):** unlock costs, vehicle costs, cargo income (including distance pay), unlock dates and growth mechanics are identical on Small, Medium and Large; never add or propose a per-size value for them. May vary by map size: number of starting towns and industries and the spacing and chain distances that place them, achievement goals, difficulty of town needs, contracts per month, contracts listed and active at once, contract difficulty; [docs/specs/gameplay-systems.md](docs/specs/gameplay-systems.md) ("Map sizes") says which of these differ today.
- **Unity visual review:** When asked to review Unity scenes or game visuals in a browser, use an actual Unity WebGL build/render where feasible; do not substitute a hand-authored HTML mockup unless the owner explicitly requests one.
- C# language level is **C# 9** (what Unity 6.3 compiles): no file-scoped namespaces, no `init`/records without polyfill, no C# 10+ features in Core. `#nullable enable` at the top of every Core file. Test method names use `Method_Scenario` style.
- Run `dotnet test dotnet/SekoyaTransit.Core.Tests` and `dotnet format dotnet/SekoyaTransit.Core.Tests --verify-no-changes` before every commit touching C#. Files must use LF line endings (run `dotnet format whitespace` if an editor wrote CRLF).
- Git: trunk-based. Unity project lives in `SekoyaTransit/` (ADR 0005, 0016). Standards are in ADR 0006; a feature is not done without tests (ADR 0007); CI per ADR 0008.

## 2b. Documentation and project management

- **Docs-as-code:** all documentation is Markdown in this repository, which is the single source of truth. Notion is not used (unreliable agent integration).
- Docs layout (create as needed): `docs/specs/` (feature/system specs), `docs/adr/` (Architecture Decision Records, one per significant technical choice), `docs/roadmap.md` (final-version overview: V1 summary plus the table of delivered V2 issues, each added in that issue's first implementation commit; no plan or next-work pointer), `docs/chat-history/` (local-only append-only weekly conversation logs, gitignored except the README; see that folder’s README).
- Use GitHub tooling for management: Issues for tasks/bugs, milestones and a GitHub Project board for the roadmap/dashboard, pull requests for changes. Use the `gh` CLI or GitHub MCP, and check for existing issues before creating new ones (avoid duplicates).
- **Epic status:** when starting work on a child issue, set both the child issue and its parent epic to In Progress on the Project board; verify both statuses.
- **Issue delivery:** finish every required delivery step for the issue before stopping—implementation, docs/ADR updates, local verification (`dotnet test` / format when C# changes; local Unity EditMode when `SekoyaTransit/` changes per ADR 0030; Unity `.meta` / scene wiring when needed), then always commit, push the feature branch, and create a pull request for owner review. Do not ask whether to open the PR, and do not pause mid-issue waiting for permission to complete those steps. The only optional step that needs explicit owner permission is a local WebGL player/preview build (see Unity validation rules). Leave the pull request open and wait for owner feedback (changes requested, or explicit go-ahead to merge). Do not merge unless explicitly authorized.
- **Issue closure gate:** never close a GitHub issue or mark its Project item Done while its implementation pull request is still open. Close it only after the PR is merged and the acceptance criteria are verified against the merged result. Prefer the PR's closing keyword to close the issue on merge; keep the board status synchronized. If an issue is closed prematurely, reopen it and restore an active board status immediately.
- **PR Test plan checklist:** tick each Test plan checkbox in the pull request body as soon as that item is verified (local tests, each green CI check, owner-validated preview, etc.). Do this before asking to merge when possible; if merge already happened with boxes still open, update the merged PR body in the same turn. Never leave verified Test plan items unticked.
- **PR checklist completion:** before completing or merging a PR, resolve every checklist item: check it when verified, or check it with a clear not-applicable explanation when it does not apply. Never leave unchecked items on a completed or merged PR; update the saved body of a merged PR in the same turn if needed. Do not imply that inapplicable work (such as feature tests for a documentation-only change) was performed.
- **PR-issue linkage:** every pull request must be created from `.github/pull_request_template.md` and its body must contain a closing keyword for its issue (`Closes #N`) so GitHub links them. Before marking a PR ready or merging, verify `closingIssuesReferences` (e.g. `gh pr view N --json closingIssuesReferences`) lists the issue; fix the body if empty.
- **Markdown verification:** after modifying any Markdown content—including GitHub issue or pull request descriptions—inspect the resulting text to confirm paragraphs, headings, lists, and checkboxes retain their intended structure. Before **every commit** that touches tracked `.md` / `.markdown` files, run `powershell -NoProfile -File scripts/check-markdown.ps1` (or the same `markdownlint-cli2` + `lychee` commands it wraps, over `git ls-files -- '*.md' '*.markdown'`) and fix failures first. Do not skip the checks; if `lychee` or `markdownlint-cli2` is missing, ask the owner before installing (see no-software-installs rule). Preferred layout (gitignored): portable Node + `markdownlint-cli2` under `.tools/`, and portable `lychee` at `.tools/lychee/lychee.exe` (same major version as CI when practical)—not a system-wide winget install. Do not push Markdown that would fail the CI **Markdown lint and link check** job. For GitHub issue/PR bodies, retrieve the saved body and verify line breaks and checklist formatting rather than trusting the submitted text.
- **Safe GitHub issue/PR body edits:** a body edit once flattened issue #173 into one paragraph because the body was fetched as separate lines and glued back together. Beyond the general rule: fetch a body with `gh ... --json body` and parse it with `ConvertFrom-Json` so it stays one string (or edit via Bash with `sed`), check that the first line has no hidden character, and remember that a checkbox count alone is not proof.
- GitHub account/repo: `sekoya-solutions/sekoya-transit` (public since 2026-10-29; the WebGL demo is on GitHub Pages, ADR 0034). Labels (type/area/version) and milestones M0-M6 exist; use them on every issue. Use `gh` (`C:\Program Files\GitHub CLI\gh.exe` if PATH is stale). Branch protection is enabled on `main` (since 2026-10-29): a pull request is required (no approvals, solo owner), the checks `Core build, test and format (plain .NET)` and `Markdown lint and link check` must pass, the branch must be up to date, and the rules also bind admins. Only squash merge is allowed and merged branches are deleted automatically. Unity EditMode is not a required check because it runs only on `main` pushes (ADR 0021, ADR 0008).
- Never hand-write Unity-generated files (ProjectSettings, Packages/manifest, .meta); let the Unity editor create them.
- Git on GitHub is the ONLY version control system. Never enable Unity Version Control (Plastic SCM) or any other VCS for the project.
- Obsidian may be used by the owner as a read-only-style viewer on `docs/`; it is not a dependency. `.obsidian/` must be git-ignored.

## 3. Mandatory: chat history logging (local only)

- Append every exchange (user prompt + assistant answer) to the **current ISO-week** file under [docs/chat-history/](docs/chat-history/README.md) **before ending the turn** (create the week file if it does not exist).
- Chat-history **log** files (week files and `archive/`) are **local-only** and **gitignored**. Never stage, commit, push, or include them in a pull request. Only [docs/chat-history/README.md](docs/chat-history/README.md) is tracked.
- Append only; never rewrite or delete past entries. Do not append to `archive/vscode-era.md` or to closed week files.
- Keep a single global entry counter across week files (continues after the archive).
- Entry format:

```text
## [N] YYYY-MM-DD HH:MM — <short title>
**User:** <verbatim or faithful prompt>
**Assistant:** <summary of answer + actions taken>
**Files changed:** <list or "none">
**Decisions / context for future agents:** <bullets>
```
